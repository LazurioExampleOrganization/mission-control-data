# Mission Control data of Lazurio Example Organization

This repository holds the Mission Control planning data of **Lazurio Example
Organization**, Lazurio's public reference Organization. All data is
fictional.

It is a `repository-db` v3 data repository on branch `v3`, mounted in the
Organization root at `mission-control/db/` inside the Mission Control app
checkout. The app code is the Organization's copy of the Lazurio Marketplace
template [LazurioTemplates/mission-control](https://github.com/LazurioTemplates/mission-control)
(release 4.1.0, in `LazurioExampleOrganization/mission-control`); this
repository holds only the Organization's data and the control plane taken
from that release's `templates/data-repo/`.

| Path | Holds |
|---|---|
| `repository-db.yaml` | The repository-db boundary: remote, branch `v3`, layout and the validate hook |
| `data/mission-control/mission-control.config.json` | Plan prefix `EX` and the Organization Admin; its other keys (publish policy, ledger paths) are history that Mission Control 4.x ignores |
| `data/mission-control/plans/` | Plans, `plans/<year>/<month>/EX-XXXX-<slug>.yaml` |
| `data/mission-control/roadmaps/` | Roadmaps, `roadmaps/<year>/RM-XXXX-<slug>.yaml` |
| `data/mission-control/TODO.tasks.json`, `DONE.tasks.json` | Task ledgers, kept as history; Mission Control 4.x neither reads nor changes them. New tasks are a plan's `proposed_tasks`, and the work itself is GitHub Issues (root `AGENTS.md`) |
| `data/mission-control/ISSUES.open.json`, `ISSUES.resolved.json` | Legacy issue ledgers, read-only; new technical issues are GitHub Issues of the owning repository |
| `data/mission-control/reports/`, `import-reviews/`, `changesets/` | Evidence, import reviews and the changesets of older Apps, kept as history |
| `scripts/validate.ts` | The validator repository-db runs before every publish and CI runs on every pull request |
| `scripts/mission-control-check.js` | Mission Control's own check of the records (Zod schemas with their refinements, rules across records, YAML parser) as one dependency-free bundle, generated by Mission Control; never edited here |
| `schemas/*.schema.json` | JSON Schemas of one record, generated by Mission Control for editors and tools; never edited here |

## Validate

```sh
bun scripts/validate.ts
```

Bun 1.4.4 is the version the release pins. It runs the App's own check, so it
passes exactly when Mission Control accepts the records: every plan and
roadmap against its schema with the refinements a JSON Schema cannot express
(a done step names its evidence, an executable step names a plan, task or
issue) and the rules across records (unique codes, references, the prefix,
at most one main roadmap). It reads only this checkout and refuses a symbolic
link in any part of a path. The CI job `validate` runs the same command on
every pull request and every push to `v3`, and is the required check of
`v3`.

## Mission Control 4.1.0 (2026-11-08)

The control plane is that of Mission Control 4.1.0 (`templates/data-repo/` of
the tag `v4.1.0`, commit `38a7680a3e9f15516b67351e531538937f3a6a01`), which
the App takes in LazurioExampleOrganization/mission-control#7: the generated
schemas, `scripts/validate.ts` with the check bundle
`scripts/mission-control-check.js`, `.gitattributes`, the workflow and the
validate hook of `repository-db.yaml`. The records did not change: 4.x reads
the same layout and record versions (`plan.v2`, `roadmap.v1`), and this data
validated unchanged with the 3.x validator before the switch. The hand-written
schemas, the `ajv` validator and `package.json` are gone; the task and issue
ledgers and the changesets stay as they are.

**Rollback**, when the new App fails and a fix forward cannot come in time:
revert the App's merge in `LazurioExampleOrganization/mission-control` with a
pull request (`git revert -m 1 <merge commit>`; the first parent is the
previous `main`) and this repository's pull request the same way, in one short
window. Every step is a new commit through a pull request, never a reset or a
force push, so data published in between stays. Taking 4.1.0 again later
means reverting those reverts.

## Writing

Plans and roadmaps are written through the Mission Control App (a draft,
reviewed and published as one fast-forward commit) or as a pull request to
`v3`. GitHub repository grants are the only access authority. Never force
push, rewrite history or store secrets, tokens or personal runtime state
here.
